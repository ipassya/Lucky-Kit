# Align existing artifacts

Use for supplied requirements, design systems, screens, technical documents, backlogs, or revisions. Preserve useful content and structure instead of forcing a migration into templates.

1. Identify relevant inputs, their owners/status/revisions when known, and what each covers. Open the content before assessing it. Links, screenshots, or exports may provide only partial evidence.
2. Map requested topics to current sources. Identify agreements, material gaps, contradictions, and duplicated rules. Explicit current user decisions govern intended scope; code establishes observed behavior. Neither automatically proves the other is correct. Recency alone does not establish approval.
3. For material conflicts, cite both sources, explain behavioral impact, recommend a resolution, and identify dependents. Apply changes already authorized. If intent remains ambiguous, preserve both interpretations and ask the smallest deciding question; continue independent work.
4. Update the owning source first, then affected flows, design, data/contracts, acceptance, and tasks. Retain established IDs and filenames. Link shared rules instead of copying them. Mark unresolved contradictions where they affect readiness.
5. Check that revised documents describe one coherent result. Report applied changes separately from proposals, implementation differences, and unanswered questions.

Small revisions may need only a paragraph and targeted edits. Use a conflict/change table when several sources need coordination. Review-only requests produce findings without editing files.

## Design systems and structured input

Preserve authoritative token names, component APIs, variants, and accessibility rules. Map screens and states to existing components; propose only missing patterns. Do not invent replacements because a template expects a value. Distinguish visual references from approved systems. If design files are inaccessible, request the relevant export or excerpt and state what remains unseen.

Connect imported requirements and backlogs to observable acceptance and planned work. Flag orphan tasks and missing coverage without inventing features to complete a matrix. Use established terminology; add a glossary only when ambiguity crosses documents.

For code/document drift, use [codebase](codebase.md) to establish implementation. Keep as-built behavior and intended changes distinct. Old verification evidence remains historical when behavior or baseline changes; affected checks remain unverified until rerun.
